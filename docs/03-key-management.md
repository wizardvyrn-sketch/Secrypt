# 03. 鍵管理設計（中核）

## 1. 問い

> マスターパスワードを保存すれば流出し得る。保存しなければ忘れ得る / 弱い。
> では個人のマスター秘密を「どこにも平文で置かず」「いつでも確実に」使うには？

## 2. 検討した方式

| 方式 | 流出耐性 | 可用性 | 手軽さ | 評価 |
|---|---|---|---|---|
| (a) 強いパスワード＋Argon2id のみ | △ 弱PWは総当たりされる | ○ 忘れなければ | ○ | 従来方式。不採用（単独では） |
| (b) キーファイル（USB 等）併用 | △ キーファイル自体をコピーされ得る | △ | ○ | 鍵がコピー可能な時点で弱い |
| (c) **TPM に鍵を封印**（PIN 付き） | ◎ 取り出し不可・総当たり制限 | △ そのPC限定 | ◎ 日常最速 | **日常用に採用** |
| (d) **FIDO2 hmac-secret**（YubiKey 等） | ◎ 取り出し不可・デバイス側PIN制限 | ○ 持ち運べる | ○ | **持ち運び/予備に採用** |
| (e) Windows Hello 署名からの鍵導出 | ○ TPM 保護 | △ そのPC限定・再登録で鍵が変わる | ◎ | 単独では脆い。**(c)のUX層として** |
| (f) **紙の復旧コード**（128bit 以上） | ○ 物理保管次第 | ◎ 電子機器不要 | △ | **最終復旧に採用** |
| (g) Shamir 秘密分散（k-of-n） | ◎ 単一シェアでは無価値 | ◎ 一部喪失に耐える | △ | **任意の上位復旧** |
| (h) クラウド/サーバに鍵預け | △ サーバ依存 | △ | ○ | 要件（ローカル完結）に反し不採用 |
| (i) **USB キーファイル＋パスワード** | ○ Vault と別保管なら安全。ただしコピー可能 | ○ 持ち運べる | ◎ 追加購入不要 | **FIDO2 の代替として採用** |
| (j) **追加PCごとの TPM スロット** | ◎ | ○ 登録済みPCならどこでも | ◎ | **複数PC利用時に採用** |
| (k) パスキー PRF（スマホ / Windows Hello パスキー） | ◎ | ○ スマホを持ち歩く | ○ | Windows での対応状況が不確実 → **Phase 0 で調査**、使えれば追加 |
| (l) 認証アプリの TOTP | ✕ 検証側に秘密を保存する必要があり、暗号鍵にならない | — | — | **不可**（ログイン認証用で、暗号化には使えない） |

**結論：(c)(d)(f) をキースロットとして併用し、(e)(g) をオプションとする。**
**FIDO2 キー未所持の間は (d) の代わりに (i)(j) を使い、FIDO2 は購入後に追加する（キースロット方式なので後から足せる）。**

## 3. 鍵階層

```
Vault Master Key (VMK) : CSPRNG 256bit。生成後、平文で永続化しない
   │
   ├─ Entry 暗号鍵 : HKDF(VMK, "entries")      … 本体の AEAD 鍵
   ├─ Header MAC鍵 : HKDF(VMK, "header")       … ヘッダ整合性
   └─ (将来) 添付ファイル鍵 等

各キースロット i:
   KEK_i = HKDF-SHA256( ikm = 要素1 ‖ 要素2 , salt = slot_salt_i , info = "pwm/kek/v1/" ‖ slot_type )
   slot_i = XChaCha20-Poly1305( key = KEK_i , plaintext = VMK , aad = header_core ‖ slot_id )
```

「要素1 ‖ 要素2」は **必ず1つ以上の“取り出し不可能 or オフライン保管”な高エントロピー秘密** を含む。

## 4. キースロット定義

### Slot type `tpm`（日常用：このPC）

- TPM 2.0 上に非エクスポート鍵を **Microsoft Platform Crypto Provider**（NCrypt）で作成。
- 鍵使用に PIN を要求（`NCRYPT_PIN_PROPERTY` / UI ポリシー）。TPM のアンチハンマリングで連続失敗をロック。
- 秘密の取り出し方（候補・PoCで決定）:
  - **案0（第一候補）**: TPM2 の sealed data object に 32byte の `tpm_secret` を封印（authValue = PIN 由来値）。
    封印データは TPM 内部の対称鍵で保護され、公開鍵暗号に依存しない＝量子耐性の弱点がない（[ADR-0004](adr/0004-tpm-seal-instead-of-rsa-wrap.md)）。
  - 案1（フォールバック）: TPM 上の RSA 鍵で `tpm_secret` を RSA-OAEP 暗号化し、暗号文をヘッダに保存。
    実装は容易だが、将来 RSA が量子計算機で破られると暗号文から `tpm_secret` が漏れ、PIN の総当たりだけが残る。
  - 案2: Windows Hello `KeyCredentialManager` で固定チャレンジに署名し、署名を HKDF で鍵化（RSA PKCS#1 v1.5 署名は決定的）。
    Hello の再登録で鍵が変わるため、**単独スロットにはしない**。
- `KEK = HKDF( tpm_secret ‖ Argon2id(PIN, salt) )`
  - Argon2id は軽め（TPM が総当たりを止めるので、PIN 単体の強度に頼らない）。
- 生体認証（顔/指紋）は「PIN 入力の代替」として Windows Hello の UI で受ける。
- **Web カメラでの顔認証について**: Windows Hello の顔認証は **赤外線（IR）カメラ** が必須で、一般的な RGB の Web カメラでは使えない。
  RGB カメラで顔認証を自作すると写真や動画でなりすましできるため、**鍵の要素としては採用しない**。
  生体認証を使いたい場合は、Windows Hello 対応の USB 指紋リーダーか IR カメラを追加すれば、アプリ側の変更なしで使える
  （生体は「TPM に PIN の代わりに本人確認させる」手段であり、生体データ自体は鍵にならない）。

### Slot type `fido2`（持ち運び用 / 予備）※保留機能

> 現在 FIDO2 キー未所持のため、**既定で無効の保留機能**として実装し、キー入手時に設定で有効化する（[ADR-0005](adr/0005-fido2-as-dormant-feature.md)）。
> Vault フォーマットにはスロット種別を予約済みのため、有効化してもデータの再暗号化は不要。

- FIDO2 セキュリティキーに `hmac-secret` 拡張付きの非発見型クレデンシャルを作成（`credProtect` レベル 2 以上、UV=required）。
- 解錠時: `hmac = HMAC(device_secret, salt_i)` をデバイスから取得（salt_i はヘッダに保存。device_secret は取り出し不可）。
- デバイス側 PIN（UV）で総当たり保護（多くの製品で 8 回失敗でロック）。
- `KEK = HKDF( hmac ‖ Argon2id(password, salt) )`
  - パスワードはここでは「二要素目」。強度が多少低くてもファイル流出時の総当たり対象にはならない。
- Windows では **WebAuthn API（webauthn.dll）** 経由で呼ぶ。Windows 10 1903 以降は非管理者アプリが USB HID の FIDO デバイスを直接叩けないため、
  OS API 経由が必須。hmac-secret / PRF の対応 API バージョンは Phase 0 で実機確認する。
- **最低 2 本（メイン＋予備）登録を推奨**。予備は別の場所に保管。

### Slot type `keyfile`（FIDO2 の代替：持ち運び用 / 予備）

FIDO2 キーがない間の「持ち運べる第二要素」。追加のハードウェア購入は不要。

- 登録時に 256bit 乱数のキーファイル（例 `vault.key`、数百バイト）を生成し、**USB メモリ等の Vault とは別の場所** に保存する。
  - 推奨: USB メモリ 2 本（メイン＋予備）、またはメイン USB＋スマホのファイル保管。
  - **Vault と同じフォルダ・同じクラウドに置かない**ことをセットアップ時に警告（同じ場所だと一緒に流出する）。
- `KEK = HKDF( keyfile_secret ‖ Argon2id(password, salt, 重め) )`
- キーファイル内にも `vault_id` と slot_id を記録し、取り違えを検知。改ざん検知用のチェックサム付き。
- FIDO2 との違い（正直な比較）:
  - FIDO2 は秘密を取り出せないが、**キーファイルはコピーできる**。USB を一時的に盗まれてコピーされても気づけない。
  - そのため、こちらはパスワード側を **重め（Argon2id 既定設定）** にし、「キーファイル＋Vault」が両方流出した場合も総当たりに時間がかかるようにする。
  - FIDO2 購入後は、このスロットを FIDO2 スロットに置き換えることを推奨。
- キーファイルは任意で **QR コードとして印刷**できるようにし、紙の予備にもできる（復旧コードとは別物）。

### Slot type `tpm`（追加PC）

複数のPCで使う場合、**PCごとに TPM スロットを1つずつ登録**する。
新しいPCでは keyfile か recovery で一度開き、そのPCの TPM スロットを追加する。以後はそのPCでも TPM + PIN で開ける。
使わなくなったPCのスロットは削除（失効）する。

### Slot type `recovery`（最終手段）

- 生成時に 160bit 以上の乱数を **ワードリスト（BIP39 互換 15 語相当、チェックサム付き）** で表示し、紙に書く/印刷する。
- `KEK = HKDF( Argon2id(recovery_code, salt, 重め) )`（エントロピーが十分なので Argon2id はおまけ）
- 生成直後にランダムな数語の再入力を求め、**書き写しを検証**してから有効化。
- 電子的には一切保存しない（スクリーンショット禁止、印刷はスプールに残らない方式を検討）。

### Slot type `shamir`（任意の上位復旧）

- 復旧用秘密を SLIP-0039 方式で k-of-n（例 2-of-3）に分割。
  シェア例: 自宅金庫 / 実家 / 信頼できる人。1枚盗まれても無価値、1枚失っても復旧可能。

## 5. 推奨構成（初期セットアップウィザード）

#### 構成1：FIDO2 キーなし（MVP の既定）

| スロット | 用途 | 必須 |
|---|---|---|
| A: `tpm` + PIN | このPCで毎日（Windows Hello の顔・指紋でも可） | 推奨 |
| B: `keyfile`（USB メモリ 1 本）+ PW | PC故障時・持ち運び | 推奨 |
| C: `keyfile`（B と同じ鍵ファイルを **印刷 QR** で予備保管）+ PW | USB 紛失・故障時 | 推奨 |
| D: `recovery` 紙 1 枚 | 全喪失時 | **必須** |
| E: `tpm`（2台目以降のPC） | 他PCで毎日（現状は1台のため未使用） | 任意 |

※ ユーザー回答（2026-10-25）: PC は基本 1 台、Vault はローカル保存、USB メモリ 1 本＋印刷 QR を予備、復旧コードは紙 1 枚。
※ B と C は同じ鍵ファイルの電子版と紙版なので、スロットとしては 1 つ（B）で足りる。QR は B の予備媒体。

#### 構成2：FIDO2 キー購入後（保留機能を有効化）

| スロット | 用途 | 必須 |
|---|---|---|
| A: `tpm` + PIN | このPCで毎日 | 推奨 |
| B: `fido2` キー#1 + PW | 持ち運び・他PC | 推奨 |
| C: `fido2` キー#2 + PW | 予備（別所保管） | 任意 |
| D: `recovery` 紙 | 全喪失時 | **必須** |

構成1→2 の移行: 任意スロットで解錠 → FIDO2 スロットを追加 → keyfile スロットを削除（キーファイルは破棄）。

ルール: **有効スロットが「recovery + 他1つ以上」を満たさない状態では保存させない。**

## 6. 運用フロー

- **USB（キーファイル）紛失**: A / C / D で解錠 → B を削除 → 新しいキーファイルで再登録。コピーされた可能性があるので VMK ローテーションも実行する。
  - 【実装状況 2026-11-01】VMK ローテーションは未実装（Phase 2）。最低限の対策として、スロットの削除・復旧コードの作り直し・PIN の変更（この PC の TPM の登録し直し）が成功したら、削除した方法がまだ載っている PC 内の自動バックアップ（`.bak1`〜）をすべて削除する（`SlotService.PurgeBackups`）。PC の外のコピー（同期・ファイル履歴・外部バックアップ）では古い方法で開けることを、確認画面で伝える。
- **PC 買い替え**: 新PCで B or D で解錠 → 新PCに A を登録 → 旧 A スロットを削除。
- **キー紛失**: C or D で解錠 → B を削除（失効） → 新キーを登録。VMK ローテーション（全再暗号化）も1クリックで実行可能にする。
- **パスワード変更**: 任意スロットで解錠 → 該当スロットを作り直す（VMK は不変なので本体再暗号化不要）。
- **定期健全性チェック**: 「最後に各スロットで解錠できた日」を記録し、長期間未使用の予備キー/復旧コードに検証を促す（使えない予備はないのと同じ）。

## 7. なぜこれで要件を満たすか

| 要件 | 根拠 |
|---|---|
| ファイル流出で復号不可 | ファイル内の全スロットが、ファイル外の高エントロピー秘密（TPM/FIDO2内部鍵、別保管のキーファイル、紙のコード）を要求する |
| マスターPWを保存しない | PWはどこにも保存しない。さらに PW 単独では鍵にならない |
| PW 流出でも安全 | PW はハードウェア要素とセットでのみ意味を持つ |
| いつでも確実に使える | 独立した3〜4経路。単一障害点がない。復旧コードは電子機器すら不要 |
